# MQTT 会话网关（进程内模拟）

本工程实现一套本地可验证的 MQTT 风格设备消息网关：用进程内的连接与订阅状态
模拟设备接入，保证不同会话、QoS 与并发场景下的投递结论一致且可解释。
核心代码位于 `com.github.h3yow.mqttsessiongatewayjava.gateway` 包，不依赖任何外部服务。

## 主题匹配规则

- 主题与过滤器均以 `/` 分层，空层级（`a//b`、首尾 `/`、空串）非法。
- `+` 匹配**恰好一层**，且必须独占一层（`a/+/c` 合法，`a/b+` 非法）。
- `#` 匹配**其自身及之后所有层（含零层）**，必须独占一层且只能位于最后一层
  （`a/#` 合法，`a/#/b`、`a#` 非法）。
- 发布主题不得包含通配符。
- 非法输入抛出 `GatewayException`，原因可区分：
  - `FILTER_EMPTY_LEVEL`：过滤器为空或含空层级；
  - `FILTER_WILDCARD_MISPLACED`：通配符未独占一层或 `#` 不在最后一层；
  - `TOPIC_INVALID`：发布主题为空、含空层级或含通配符。
- 路由只把消息投递给过滤器匹配的订阅；同一会话多条订阅命中同一主题时只投递一次。

## 投递与确认语义

- **QoS.AT_MOST_ONCE（至多一次）**：在线投递即完成，不跟踪、不需确认；
  离线时进入持久会话积压，重连后补投一次。
- **QoS.AT_LEAST_ONCE（至少一次）**：在线投递后登记为待确认（在途）；
  未确认的消息在客户端重连时按原 messageId 重投，直到被确认为止。
- **发布侧 QoS 与协商**：`publish(topic, payload, qos)` 可带发布方 QoS；
  不带 QoS 的旧签名 `publish(topic, payload)` 等价于发布方按至少一次（向后兼容）。
  每条投递的最终等级取 **min(发布方 QoS, 订阅方 QoS)**：任一方只保证至多一次，
  整体就按至多一次处理（不进在途、不需确认）；双方都至少一次才登记待确认。
  离线积压条目记录的是**协商后**的 QoS，因此重连补投、是否需要确认都按协商等级走，
  不会各算各的。
- **持久会话**：`connect(clientId, true)` 创建；断开后保留订阅、离线积压与待确认，
  重连时 `connect` 返回需补投的消息列表（离线积压 + 未确认消息），不丢不重。
  非持久会话断开即清除全部状态。
- **确认（ack）**：
  - 确认成功：消息从待确认与在途集合移除；
  - 重复确认：拒绝，原因 `ACK_DUPLICATE`；
  - 非对应订阅者的确认（含未知 messageId）：拒绝，原因 `ACK_NOT_PENDING_FOR_CLIENT`；
  - 会话不存在：拒绝，原因 `SESSION_NOT_FOUND`。

## 重启恢复（本地持久化）

配置 `gateway.data-dir` 后启用重启恢复，数据只写本地目录，**不依赖任何外部服务**：

- 每次状态变更（连接/断开/订阅/发布/确认）后，网关在锁内把全量快照原子落盘
  （先写 `gateway-state.json.tmp` 并 `fsync`，再原子 rename 为 `gateway-state.json`），
  崩溃后磁盘上要么是旧快照、要么是新快照，不会出现半截文件。
- 落盘内容：全局消息 id 序列、每个**持久**会话的订阅（过滤器原文 + 订阅 QoS）、
  离线积压（消息 + 协商后 QoS）、未确认消息、最近的已确认消息 id（有界 1 万条）。
- 用**新进程**指向同一数据目录启动时：
  - 持久会话连同上述状态原样恢复，恢复后一律为离线，等待客户端重连；
  - 重连时未确认消息与离线积压照旧补投，不丢不重；已确认过的消息不会再次出现，
    对历史已确认消息再确认仍返回 `ACK_DUPLICATE`；
  - 未确认消息恢复后仍占用网关在途额度；消息 id 从上次序列继续递增、不复用；
  - **非持久会话从不落盘**，重启即彻底消失。
- 数据目录读写失败以 `PERSISTENCE_IO_ERROR` 明确报错。
- 不配置 `gateway.data-dir`（留空）时为纯内存模式，行为与之前一致。

## 容量与背压

配置项（`application.properties`，前缀 `gateway`）：

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| `gateway.backlog-capacity` | 1000 | 单会话离线积压上限。任一离线目标会话积压满时，发布被**整体拒绝**（`BACKLOG_CAPACITY_EXCEEDED`）。 |
| `gateway.max-in-flight` | 10000 | 全网关在途（已投递待确认）消息上限。若本次发布会使在途**超过**上限，发布被**整体拒绝**（`BACKPRESSURE_LIMIT_EXCEEDED`），确认后释放额度。 |
| `gateway.data-dir` | 空（纯内存） | 本地持久化数据目录，配置后启用重启恢复。 |

拒绝语义（卡死、互不牵连）：

- **预检先于任何投递**：发布先在同一临界区内算清全部目标，并统计本次将新增的
  积压条目数与在途数；只要任一目标会超积压上限、或在途 `现有 + 本次新增 > 上限`，
  就在分配消息 id、产生任何投递之前整体拒绝——不会投一半留一半，被拒发布也不消耗消息 id。
- 实际统计到的积压量、在途量，在任何一次**被接受**的发布后都严格不超过各自上限。
- 积压满只得到**明确拒绝**（`BACKLOG_CAPACITY_EXCEEDED`），绝不静默丢消息。
- 容量按会话/在途分别记账：某个设备占满自己的积压额度，不影响其他设备的发布、
  订阅、确认，也不会阻塞网关；至多一次的协商结果不占用在途额度。

## 并发一致性

路由判定与投递状态变更在同一临界区内生效，因此多线程并发发布/订阅/确认时，
同一主题的每次路由结果都是一致快照：匹配订阅者无遗漏、无重复、无不匹配者。
确认恰好一次生效，并发重复确认全部被识别为 `ACK_DUPLICATE`。

## 本地验证

无需任何外部服务，直接构建并运行测试：

```bash
mvn test
```

测试覆盖（日志会打印每一步的输入、会话状态与投递判定依据）：

- `TopicFilterTest`：通配符边界（`+`/`#`、混合、零层匹配）与非法过滤器/主题的可区分拒绝；
- `DeliveryAckTest`：路由不投递给不匹配订阅、两种 QoS 语义、重复确认与错误订阅者确认的可区分拒绝；
- `OfflineBacklogTest`：持久会话离线积压、重连补投不丢不重、积压超容量拒绝、背压限流（严格整批预检）；
- `ConcurrencyTest`：16 线程并发发布路由一致性、并发确认恰好一次、慢客户端明确拒绝且不阻塞网关；
- `RestartRecoveryTest`：**真正新建/重启网关实例**（`new Gateway(同一 @TempDir 配置)`，
  不是同进程断开重连）验证订阅/积压/未确认/已确认记录恢复、已确认消息不复发、
  非持久会话重启消失、连续多次重启状态稳定，且快照文件确实落在本地目录；
- `PublishQosNegotiationTest`：四种发布/订阅 QoS 组合的协商取低、离线积压与重连补投按协商等级、
  旧签名发布的向后兼容；
- `CapacityIsolationTest`：多离线目标时容量预检整批拒绝（无一多收）、在途严格不超上限、
  单设备额度占满不牵连其他设备的发布/订阅/确认。

运行时日志关键字（可直接据此还原每一步判定）：

- `[connect]` / `[disconnect]`：输入 clientId、persistent、积压与待确认数量、补投条数及判定依据；
- `[subscribe]`：clientId、过滤器原文、订阅 QoS、在线状态；
- `[route]`：messageId、topic、目标 client、发布/订阅 QoS、协商后 effectiveQos、投递判定；
- `[publish-accept]` / `[publish-reject]`：被接受后的在途用量，或拒绝原因（容量/背压）与预检数值；
- `[ack-ok]` / `[ack-reject]`：确认释放在途，或重复/非订阅者确认的可区分原因；
- `[persistence]` / `[restore]`：快照落盘/加载路径、恢复的每个会话各项计数。

手动体验重启恢复也只需本地目录（两个进程用同一 `-Dgateway.data-dir` 即可）：

```bash
mvn -q spring-boot:run -Dspring-boot.run.arguments="--gateway.data-dir=./data/gateway"
# 停掉后再次用同样参数启动：持久会话与离线积压、未确认消息原样恢复
```
